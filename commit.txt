Three real, distinct sources, all in the ligand-design path rebis.ligand actually runs:

ligand_from_site_pdb.py's find_ligand_smiles_from_pdb calls Chem.MolFromPDBBlock on real HETATM records straight from a fetched structure — plenty of real PDB files carry an atom with a blank or non-standard element column, which RDKit's parser correctly rejects and just as correctly writes about. Silenced with RDLogger.DisableLog('rdApp.*') for the higher-level Post-condition messages, plus a direct fd-level redirect (_silence_rdkit_native) for the valence check inside the same sanitize=True pass that RDLogger's channel doesn't cover.

ligand_improvements.py's generate_substrate_analogs tries many combinatorial molecule constructions by design — Murcko-scaffold decoration, chain extension, ring substitution — deliberately forcing a new bond onto an atom that may already be valence-saturated, and RDKit's sanitizer is what's supposed to catch that. Three call sites (murcko_decorated, chain_extend, ring_sub) were unguarded; a fourth (_try_add_candidate's own Chem.MolFromSmiles) already used this file's own _silence_rdkit() context manager, which does a correct OS-level stderr fd redirect. Applied the same wrapper to the other three.

None of this changes what gets accepted or rejected — every one of these was already a correctly-discarded invalid candidate, exactly as intended. It only stops RDKit's native logger from making a correct rejection look like a crash.
